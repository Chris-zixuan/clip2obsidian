# 剪藏入库细则

本文件只写**流程、边界与示例**。字段字典、标签词表、目录规则一律现场读知识库的
`9_系统/协作约定.md` —— 不在这里复制规范副本（历史教训：副本漂移会写入已废弃的标签）。

## 一、输入长什么样

L2 的产物 `work/{id}.md` 由两段组成：

```markdown
<!--c2o:meta
title: 摄影师不用熬夜选片了
source_url: https://www.bilibili.com/video/BV1xx411c7mD
author: 某UP主
published: 2026-09-01
clipping_type: bilibili-video
platform: bilibili
native_id: BV1xx411c7mD
extractor: whisper:mlx:large-v3
-->

## 转写全文

**[00:00]** 出门拍了2000张照片，用AI五分钟选完……
```

- 来源块是 HTML 注释：渲染后不可见，**信息进属性后要删掉整块**
- `extractor` 说明这段文字是怎么来的：`subtitle:local:srt`（本地字幕，可信度高）、
  `whisper:mlx:*` / `whisper:faster:*`（自动转写，可能有同音字错误）、
  `agent:vision`（图文，由 agent 读图）、`cloud:*`（云端 API）
- 自动转写的正文里会有 `> [!warning]` 提示，**保留它**：读者需要知道这份文本未经校对

## 二、字段映射

以库内规范为准，通常是这样对应：

| 来源块 | 知识库属性 | 注意 |
|---|---|---|
| `title` | `title` | 必要时再精简：剥掉截断尾巴、营销腔 |
| `source_url` | `source_url` | 空值就**不写这一行**，不要写 `unknown` 或 `-` |
| `author` | `author` | 库内要求列表形式时按规范写，值用 `[[作者]]` 或裸值 |
| `published` | `published` | 日期书写方式（裸值 / 引号）**现场读规范确认** |
| — | `created` | 入库当天日期 |
| `clipping_type` | `clipping_type` | 直接用，不要自创值 |
| — | `类型` | `clippings`（封闭值域之一） |
| — | `tags` | 从词表选 1–3 个；不确定就留空并说明 |

**绝不编造**：`author` 缺失就是缺失。填一个猜测的作者会污染检索，比空着糟糕得多。

## 三、标签怎么选

1. 先读 `9_系统/协作约定.md` 的标签词表（技术域 / 个人域）
2. 按内容主题选 1–3 个最能帮助检索的；宁少勿滥
3. 找不到合适的就**留空**，在回复里说明「这篇没找到合适的受控标签，需要你补」
4. 不要用 `类型/xxx` 这类伪层级标签，也不要把 `clippings` 写进 `tags`

## 四、图文素材

图文 md 是骨架：

```markdown
## 图片

> 以下每张图等待 agent 读取后补写文字说明。

<!--img: /Users/.../work/1f2a5c3e3584/images/001_封面.jpg-->
**图 1**：

<!--img: /Users/.../work/1f2a5c3e3584/images/002_步骤.jpg-->
**图 2**：
```

流程：

1. **逐张读图**：用图片路径读取，写下图内文字（OCR 性质）与关键信息
   （界面、步骤、数据、结论），替换 `**图 N**：` 后面的空白
2. 图与图之间若有前后关系（步骤、对比），在文首用一两句话串起来
3. 图片本身**不搬**：知识库规则禁止 AI 脚本批量搬附件，请用户在 Obsidian 里
   用 CAL 插件的「收集附件」命令处理
4. 补完正文后再入库

## 五、复核与库级操作

写入后用 yzx-obsidian 的能力做这几件事（它的 `references/cli-reference.md` 有完整命令）：

```bash
obsidian unresolved | grep "文件名"     # 确认没有新增断链；无输出才算干净
obsidian tags counts                     # 抽查标签分布是否合理（可选）
```

- 刚写完可能因索引未重建而误报，等 1–3 秒再查
- 需要改属性：`obsidian property:set`（显式传 `path=` / `file=`）
- 需要移动 / 重命名：`obsidian move` / `obsidian rename`，**不要用 `mv`**
- 移动后必须再跑一次 `obsidian unresolved`

## 六、常见情况处理

| 情况 | 处理 |
|---|---|
| 来源块缺 `author` / `published` | 不写这两行，完成报告里提一句「元信息缺失，需要时请补」 |
| 没有找到合适标签 | 留空并说明，不要造标签 |
| 重名笔记已存在 | **停下来问用户**：覆盖、改名、还是放弃？绝不静默覆盖 |
| md 里没有来源块 | 说明这份 md 不是本项目产物（可能来自旧流程），让用户确认来源 |
| 转写质量明显差（同音字多） | 如实告知，建议改标题/标签时保守，必要时让用户决定是否入库 |
| 一次要入库多篇（≥3） | 先列清单（标题 + 目标文件名 + 标签）征得同意，再逐篇执行 |
| 图片很多（>20 张） | 提示用户这会让读图很慢，可先入库正文、图片分批处理 |

## 七、完成报告

入库结束后，用一小段话向用户交代：

- 落了哪几篇、文件名与标签分别是什么
- `obsidian unresolved` 的结果（是否干净）
- 有哪些字段缺失、有哪些标签没把握
- 图片是否还需要用户用插件收进附件目录

不要只说「已完成」——用户需要知道哪些地方是需要他补的。
